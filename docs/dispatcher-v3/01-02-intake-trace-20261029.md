## Implemented credential and ownership chain

`src/services/pttProvenance.js` is the shared internal issuer and checker. A principal requires either a verified, unexpired stored session whose account is active, or a real unlocked radio token assigned to an active, resolvable account. Socket.IO session proof requires the signed cookie. HTTP handlers use the session established by Express or the supported radio-token path. A canonical callsign lookup, claimed dispatcher flag, supplied device ID or current presence cannot mint AI actor authority.

The issuer reads enabled channel grants from `user_channel_access` joined to `channels` using the authenticated **account ID**. Principals and their grant arrays are frozen and registered privately in process-local weak collections. Client JSON, an `authenticated` boolean, or a serialized copy of a legitimate principal or transmission cannot reproduce that proof. Socket connection IDs and opaque server-derived HTTP credential connection handles distinguish owners; raw cookies, session IDs and radio tokens are not copied into envelopes or public PTT payloads.

The runtime manager then binds the owned grant to the complete configured channel/profile/dispatch-center mapping. Its snapshot includes disabled profiles, so finding one running dispatcher is insufficient evidence of unique channel ownership. Channel IDs and room keys must agree; ambiguous display names, duplicate center mappings and runtime/configuration mismatches fail closed. Profile creation, updates, deletion and configuration reads refresh the mapping. A failed complete configuration read invalidates the snapshot until a successful refresh. The earlier single-profile read cannot overwrite a newer complete snapshot during startup.

Only after this binding does V3 resolve the authenticated speaker against Command Link in that dispatch center. A missing or ambiguous speaker prevents transcript-triggered actions even when a spoken target would resolve. The immutable speaker stays separate from the requested target: an authorized A1 request concerning B2 may target B2, but B2 does not become the actor. Existing CAD action scopes and mutation verification still apply.

These records establish intake ownership. They do not claim continuous credential revocation or authorization freshness after every asynchronous boundary; that enforcement remains 01-05.

## Immutable turn record and downstream propagation

At accepted V3 PTT start, before asynchronous speaker resolution or speech recognition, the runtime allocates a unique turn ID and a monotonically increasing intake sequence within its runtime generation. The frozen identity records runtime/profile/generation, dispatch center, canonical channel and room, transmission ID, authenticated account and connection, credential type, speaker reference, source and accepted capture-start time.

At end, the runtime consumes the exact transmission once and seals its audio capture before awaiting identity resolution or transcription. The final frozen envelope adds the authoritative center-resolved speaker and capture-end time while retaining the original frozen intake identity. The finalized envelope is carried unchanged through transcription, planning, materialization, execution, compound-action steps, response composition, output and diagnostics. Async-local turn context also preserves ownership through existing gateway and emergency-response call paths. Empty capture, unresolved identity, STT failure and output failure retain a traceable originating identity or envelope.

Start/end timestamps are **server-observed accepted capture timestamps**, not measured physical microphone timestamps. The original stop time is sealed before drain completion. A delayed drain callback cannot replace it with the callback time or consume a newer capture with the same callsign.

The live executor requires a trusted, center-resolved envelope independently of the model's plan. Model-supplied speaker/account/envelope fields are not authority. Recording generation and intake sequence does not itself change execution ordering or cancel late work.

## Duplicate events and ambiguous legacy audio

Repeated starts for an active source retain the original capture. The matching end consumes that capture synchronously, so another end cannot launch a second transcription or action. A completed internal source is recognized through its private weak root-completion association even after bounded runtime ID history is evicted. Normal, drained and forced completions preserve that same source identity.

Existing optional client request IDs are also used when supplied. They are scoped to the proved account, authenticated connection and canonical channel, held privately, and bounded to **2,048 entries** with a **10-minute lookup lifetime**. Pruning occurs on access and insertion, so expired records may remain in memory while idle but cannot match after the next lookup prunes them. A known mismatched end is rejected; a known completed request replay is suppressed. This optional wire-request history is separate from the internal completed-source weak association.

The audio-listener contract supplies a unit/callsign without a connection or transmission ID. Frames are dropped when multiple captures with that callsign make assignment ambiguous. Overlapping different accounts or connections with the same callsign invalidate the competing captures; later starts remain blocked until matching ends for all known sources arrive. A third start cannot reopen attribution while either original source is unresolved. Ambiguity bookkeeping is bounded to **128 callsigns and 128 sources per callsign**. If that bookkeeping overflows, the affected ownership state fails closed until the runtime is deliberately stopped; missing evidence is never treated as proof. No service restart was performed during this work.

## Historical intake trace before implementation

The following findings were recorded during read-only preparation before 01-02 coding began. They explain the original defect and implementation boundary; they do not describe the completed implementation above.

The managed runtime receives signaling events but forwards only channel/unit identifiers and legacy positional values. V3 creates a correlation ID at capture start, yet has no immutable turn envelope, intake sequence or runtime-generation record. Speech capture retains a start timestamp internally and drops it from returned transmissions. Scheduling occurs after STT completion; changing that scheduling is 01-03, not a completion claim for 01-02.

Credential verification and canonical callsign lookup must remain distinct. The Socket.IO authentication path can resolve a claimed login when no session cookie was verified; that lookup must not mint an authenticated AI actor. The radio-token path proves a device, but needs its successfully resolved, enabled assigned account before it can prove a CAD speaker. The HTTP PTT path's presence check is not proof of ownership by the current request. The authenticated notify-PTT endpoint is another intake path through two compatibility forwarding layers.

Existing server-owned channel grants are available in `user_channel_access` joined to enabled `channels`. Read them using the authenticated account ID, not a client-supplied callsign, dispatcher flag or current presence. The available evidence chain is account credentials, account channel grants, an unambiguous configured channel-to-center mapping, then authoritative speaker resolution in that center. The tracked schema does not establish a separate account-to-CAD-center foreign key. A bare channel name, or simply finding one runtime for a client-selected channel, does not establish permission.
